# 使い方

本ドキュメントでは、SQuidLite3のセットアップ、起動手順、認証、日常の同期運用、およびCLIコマンドの仕様を説明します。

## 前提環境

以下のランタイムがインストールされている必要があります。

- Python 3.10 以上
- Node.js 22 以上（npm を含む）

## 初回起動手順

ZIPファイルを解凍したディレクトリで、各OSに対応する起動スクリプトを実行します。

- macOS: `Start.command` をダブルクリック（またはターミナルから実行）
- Windows: `Start.bat` をダブルクリック（またはコマンドプロンプトから実行）
- Linux: 端末で `sh scripts/start.sh` を実行

### 起動スクリプト (scripts/start.py) の処理の流れ

起動スクリプトを実行すると、内部で以下の処理が順次自動実行されます。

1. 実行環境の検証（Python 3.10以上、Node.js 22以上、npmの有無を確認）
2. 依存関係の導入（`npm ci --ignore-scripts --no-audit --no-fund` により定義通りの固定バージョンをインストール）
3. ローカル認証（`python3 archive.py login` を呼び出し、対話形式で認証）
4. カタログの取得（`python3 archive.py refresh-catalog` により現行イカリング3のクエリ定義を取得）
5. 初回同期（`python3 archive.py sync` により最新の戦績・サーモンラン履歴等を取得）
6. 定期実行の構成:
   - macOS: LaunchAgent の登録（`python3 archive.py install-service` により、バックグラウンドで120秒ごとに自動収集を実行）
   - 他のOS (Windows / Linux): 前面監視（`python3 archive.py watch` により、画面を開いたまま120秒間隔で収集を継続）

## 認証に関する重要事項

- ニンテンドーアカウントのパスワードは、自動で起動するNintendo公式のWebブラウザー画面にのみ入力してください。本ツールのCLIや端末画面にパスワードを直接入力することはありません。
- ログイン完了画面で「この人にする」ボタンを右クリックしてリンクアドレス（`npf71b963c1b7b6d119://...` で始まるURL）をコピーし、端末の入力プロンプトに貼り付けてください（入力文字は非表示となります）。
- コピーした認証リンクや取得されたセッショントークンは機密情報です。GitHubのIssueやPull Request、公開チャット、掲示板等に絶対に送信・貼付しないでください。

## 検証状態に関する注意

本人認証と実データの継続同期は実施済みです。公開サンプル・人工データのテスト成功と、実アカウントの全取得完了は別です。未処理ジョブ、取得不能詳細、対象外ランキング、未確認の参加条件を status / audit で確認してください。

## コードと実データの分離・保存先

本ツールでは、Gitリポジトリ（ソースコード）と取得した実データを明確に分離して管理します。

- 既定のデータ保存先:
  - データ親ディレクトリ: `~/Documents/イカリング3アーカイブ`
  - メインデータベース: `~/Documents/イカリング3アーカイブ/database/archive.sqlite3`
- 保存先ディレクトリの変更:
  - 環境変数 `IKARING_ARCHIVE_DATA_DIR` を設定することで、データ親ディレクトリを変更できます。
  - 各CLIコマンドで `--db <PATH>` オプションを指定することで、任意のSQLiteデータベースファイルを指定できます。
- nxapi認証情報の保存先:
  - nxapiの標準保存先に安全に格納されます。
  - 環境変数 `NXAPI_DATA_PATH`、または各コマンドの `--nxapi-data <PATH>` オプションで保存場所を指定することも可能です。

## CLIリファレンス (archive.py)

各種操作を直接実行するためのコマンドライン構文です。

### 共通オプション

```sh
python3 archive.py [--db DB_PATH] <サブコマンド> [サブコマンドオプション]
```

`--db` を省略した場合、既定値（`~/Documents/イカリング3アーカイブ/database/archive.sqlite3`）が使用されます。

### サブコマンド一覧

- **状態確認・初期化**
  - `python3 archive.py init`
    データベーススキーマを適用し、現在の状態サマリーを表示します。
  - `python3 archive.py status`
    現在の記録件数、ジョブキューの消化状況、未取得件数等を表示します。
  - `python3 archive.py audit`
    イカリング3のAPI定義とローカルDBの取得状況を突き合わせ、網羅性と未対応経路を監査します。NAS の正本に対しては `python3 scripts/nas_archive.py audit` を使います。出力の `event_evidence` は公開済み応答にあるイベント記録の証拠を集計したもので、イベントIDやアカウント等の識別子は出力しません。`fest_event_details` と `fest_events_with_player_result` は別であり、`big_run_event_records` と `big_run_events_with_positive_highest_job_score` も別です。`team_contest_max_observed_attend` は観測最大値であり取得済みシフト数ではありません。また、`classified_match_counts` が0であっても未参加や全取得完了の証拠ではありません。
  - `python3 archive.py verify`
    保存されている全レスポンス本文のSHA-256ハッシュ整合性を検証します。

- **カタログ・認証・収集**
  - `python3 archive.py login`
    ブラウザー連携による対話的ローカル認証を実行します。
  - `python3 archive.py refresh-catalog`
    最新のイカリング3 WebリソースからGraphQLクエリ定義・ハッシュを抽出してDBを更新します。
  - `python3 archive.py sync [--account ACCOUNT] [--nxapi-data PATH] [--budget BUDGET] [--delay DELAY]`
    未取得の詳細ジョブや新着の対戦・サーモンラン一覧を同期します。
    - `--budget`: 1回の同期で実行する最大リクエスト数（既定値: 250）
    - `--delay`: リクエスト間の待機秒数（既定値: 1.5）
  - `python3 archive.py watch [--interval INTERVAL]`
    定期的に `sync` を実行する前面常駐プロセスを起動します（既定間隔: 120秒、最小値: 60秒）。

- **バックアップ・エクスポート・インポート**
  - `python3 archive.py backup <DESTINATION>`
    SQLiteのオンラインバックアップAPIを使用し、指定したパスへ安全にデータベースのコピーを作成します（既存ファイルの上書きは防止されます）。
  - `python3 archive.py export <DIRECTORY>`
    保存されたレスポンス本文をJSONファイルとして、また画像等のメディアをバイナリとして指定ディレクトリに出力し、`manifest.jsonl` / `assets.jsonl` を生成します。
  - `python3 archive.py import <DIRECTORY> --account <ACCOUNT>`
    外部ダンプファイル（nxapi形式等）からレスポンスを再構築してインポートします。

- **プラベとオープンの事後タグ**
  - `python3 archive.py tag add --match-key MATCH_KEY --tag 対抗戦`
  - `python3 archive.py tag remove --match-key MATCH_KEY --tag 対抗戦`
  - `python3 archive.py tag list`
    タグは、APIが区別しない意味を後から付ける。プラベではエンジョイ、対抗戦、イカップル、オープンでは下げラン、練習、エンジョイ、ガチが候補である。候補以外のタグも付けられる。試合の母集団は変わらない。アカウントが複数あるときは `--account` が必要。
  - 記録の閲覧画面は `python3 scripts/desktop_app.py` で開く。NAS を正本にしている Mac では、データベースのパスを付けずに起動する。画面からタグを追加・削除できるのはプラベとオープンだけである。一覧はジャンル、ルール、試合日時、自分のブキ名、タグ、検索文字列で絞れる。一覧と詳細に出すジャンル名は、人数で分けた分類である。分類が無い記録は不明と出す。期間は詳細の試合日時だけで、試合日時が無い記録は期間を指定すると含まれない。収集状態には、保存試合、詳細の待ちと取得不能、未了のジョブ、監査記録、取得範囲の照合、直近の認証事故と収集エラーが出る。その下に履歴7経路を、最新の履歴、レギュラーマッチ、バンカラマッチ、Xマッチ、イベントマッチ、プライベートマッチ、バイトの順で出す。各行は、確認済みか遅延かと、最終成功時刻か未確認かである。行が無いもの、時刻を読めないもの、サーバが遅延としたもの、表示時点で10分を超えたものは遅延とする。取得中と取得失敗のあいだは出さない。表示中は60秒ごとに、同じ取得結果の時刻から描き直す。未了のジョブは pending、retry、awaiting_scope の合計である。照合済みは、取得範囲を照合し終えた印が真のときだけである。オープンとプラベの人数区分ごとに、試合数、タグなし、タグごとの試合数を出す。区分をまたいだ合計は出さない。ルール別の勝敗と、レート系列の最新・増減・最低・最高・点数を出す。区分やルールをまたいだ合計は出さない。勝敗から作った系列と、ウデマエポイントの増減は出さない。各系列の下に、軸と目盛りのあるグラフと、同じ数値の表を置く。キケン度は表示のときだけ百分率にする。1点の系列は線を引かない。旧分析表は欠落があるため利用できず、画面上のボタンも無効化している。全情報の書き出しは準備中である。バックアップ操作は未実装である。この画面は統合GUIの完成ではない。

- **旧モード別・ルール別の派生データベース**
  - `python3 archive.py slice-export <DESTINATION>`
    全source表の全行・全列・型付き値をlosslessなshardに保存し、mode/rule selectorを含む検証済みのimmutable generationを作る。既存世代は上書きせず、新世代の検証後に `current-generation.json` を最後に更新する明示的なexportであり、収集thread内では実行しない。
  - NAS の正本に対しては `python3 scripts/nas_archive.py slice-export` を使う。書き先は NAS の `database/slices` に固定され、別のパスは受け付けない。
  - 旧sliceは `analysis_slice` に相当する不完全な派生物である。旧GUIで一覧や絞り込みに使えることは、その範囲外の情報まで含む証明ではない。全情報分析には使用せず、全情報baselineの `slices/` と混同しない。

- **全情報baseline・差分世代の読出し**
  - lossless baselineは全source表を表shardとvalue chunkに分けて保持し、各SQLiteデータファイルを20 MiB以下にする。全行・全列・空表・SQLite schema object・column xinfo・foreign key・行数・観測可能なsource rowidと型付き値を保持する。巨大なTEXT・BLOBは順序付きchunkから復元する。元データにある参照切れは修正せずそのまま保存する。raw統合SQLiteをreader用に復元する必要はない。
  - `by-mode/` は15の既知分類、観測された追加分類、未分類のselectorを持つ。`by-rule/` は観測されたmodeと観測された全ruleの組を、0件の組も含めて列挙する。selectorは対象試合への入口であり、全表データは共通shardにある。ファイル数はsource内容により変わる。
  - 差分世代はbaseline以降の変更を順番に適用する。native SQLite transportまたはlossless SQLite shardとして、全source tableのschema等のmetadataと変更行の全型付き値を保持する。差分内の `xlsx/` は差分transportをlosslessに表したもので、現在の全source状態のXLSXではない。feed導入前の取りこぼしを埋める初回世代はbaselineから全sourceを照合するreconciliationで作る。schema変更やwriter guardの未導入・未検証があればbaselineから新しいreconciliationを始め、旧chainは保持する。
  - publisherのscopeは別々である。GUI publisherは `gui/index.html` だけを公開する。SQLite component publisherは全値入りshard群とcomponent indexを公開するが、全情報XLSXやglobal generation index/latestを完成させない。full baseline publisherはunified snapshot・lossless slices・全情報XLSXをまとめ、delta publisherはそのbaselineに束縛した差分chainを公開する。どれか一つのreceiptを他のscopeの成功とみなさない。
  - `--root` はbaseline package、各 `--delta-dir` は一世代分のローカルdelta packageを指す。prepared directoryでもremoteから取得したdirectoryでもよいが、元 `delta-plan.json` と `plan.files` の全artifactを保ち、remote-onlyの場合は `deltas/generations/<id>/index.json` が示す全artifactを各 `local` 相対パスどおりに配置する。publisherはplan自体も遠隔artifactとして全byte/SHA readbackし、`index.json` の `files` 最後のentryと `plan_sha256` に束縛している。remote `index.json` はpackage内に `index.json` として含めることができ、readerは存在する場合にplan・全file inventory・SHAとの厳密な一致を検証する。prepared packageとremote-only packageは同一generationのplan・宣言artifactで構成する。lossless shard transportでは巨大な `changes.sqlite3` は準備時だけの検証用cacheでありreaderに不要だが、native SQLite transportでは `changes.sqlite3` 自体が宣言artifactとなる。どちらもunified `source.sqlite3` のreaderへの復元は不要である。

    ```sh
    BASELINE_DIR='<local-path-to-verified-baseline-slices>'
    DELTA_DIR_1='<local-path-to-delta-generation-1>'
    DELTA_DIR_2='<local-path-to-delta-generation-2>'

    python3 archive.py shard-list --root "$BASELINE_DIR" \
      --generation '<baseline-id>' \
      --delta-dir "$DELTA_DIR_1" \
      --delta-dir "$DELTA_DIR_2"

    python3 archive.py shard-read --root "$BASELINE_DIR" \
      --generation '<baseline-id>' \
      --delta-dir "$DELTA_DIR_1" \
      --delta-dir "$DELTA_DIR_2" \
      --table matches --limit 100
    ```

  - `--delta-dir` は繰り返し指定でき、適用順に並べる。reset世代で旧chainが置き換わった場合は、そのreset世代以降を現在のchainとして読む。`--generation` は常にbaselineの期待世代IDを検査する指定であり、最新差分世代のIDではない。世代のsource SHA-256、親・baseline binding、schema、全proof、ファイルハッシュに不一致があれば読出しを拒否する。
  - `shard-list` はbaselineと差分を適用した現在の全table・schema metadata、baseline/latest generation、適用したdelta IDをJSONで返す。`shard-read` は全表の現在行をJSONLで返す。`--table` で表を選ぶ。`--mode MODE` または `--mode MODE --rule RULE` は `matches` のselector読出しに使い、現在の分類とmatch行から対象を選ぶ。selector出力は選択行だけだが、headerがその範囲を示し、全source表は通常の表読出しで取得できる。
  - JSONLの各値はSQLite型とencodingを明記する。INTEGERは10進文字列、REALは `float.hex()`、TEXTはUnicode文字列（NULを含む値もJSON内で保持）、BLOBはhexで表す。NULLも独立した型として表す。全表読出しの各行にはstream ordinalと、保持できる場合は元の `source_rowid` を型付き値で出す。WITHOUT ROWIDなど元rowidがない表ではnullとなる。ordinalは出力順の番号でありsource rowidとは別である。headerには表の列・xinfo・foreign key・全表行数等を含む。
  - 人工fixtureのテスト成功は、NAS/Driveの実データ全体を読み戻し照合できた証明ではない。現在の全情報baseline XLSXとglobal generation indexを含む一連の実公開・継続同期は未完了である。状態・時刻の確認は[クラウドデータ案内](cloud-data-map.md)を参照する。

- **レートのグラフ**
  - `python3 archive.py gui`
    ジャンルと指標ごとにグラフと表を作る。色は NOAHS の卓上と紙。チョーシはブキ記録の公式値を取得時点ごとに保存し、勝敗から推測しない。所持ウデマエポイントは現行APIから取得できないため、増減値を累積値に見せかけない。
    生成HTMLには同梱したSplatoon2 Unifiedフォントが埋め込まれる。縦横の軸、Y目盛り、水平補助線、日付目盛り、ゼロ線、最新値・増減・最低・最高・点数が表示される。表示値だけ読みやすい桁に整え、SQLiteの正本値は変えない。
    別のフォントを使う場合だけ、`IKARING_ARCHIVE_FONT` にOTFファイルのパスを指定してから実行する。

- **人が開く表**
  - 旧CLI `python3 archive.py export-xlsx` と `python3 archive.py published-xlsx` は退役済みで、どちらも `LEGACY_ANALYSIS_XLSX_RETIRED` を標準エラーへ出して終了コード 4、標準出力は空となる。`export-xlsx` は Store を開く前に拒否され、いずれも旧ブックの読取・生成・更新をしない。`python3 scripts/nas_archive.py export-xlsx` もSSHやファイル取得の前に拒否される。desktop API `/api/published-xlsx` は認証とクエリ検査を維持して HTTP 410 を返し、画面の旧ダウンロードボタンは無効である。全情報の書き出しは準備中であり、旧ブックを代用しない。

- **SQLクエリ実行**
  - `python3 archive.py sql "<QUERY>"`
    読み取り専用モード（`PRAGMA query_only=ON`）でSQLiteに対してSQLを実行し、結果をJSON形式で出力します。

- **macOSサービス登録**
  - `python3 archive.py install-service [--interval INTERVAL] [--account ACCOUNT] [--nxapi-data PATH]`
    macOSの `LaunchAgent` として定期取得ジョブ（既定: 120秒間隔）を登録し、即時ロードします。

## macOS 常駐サービスの管理

macOSで `install-service` により登録された常駐ジョブ（LaunchAgent: `local.ikaring3.archive`）の制御コマンドです。

- **常駐サービスの登録解除（停止）**
  ```sh
  launchctl bootout gui/$(id -u)/local.ikaring3.archive
  ```

- **常駐サービスの再登録**
  ```sh
  python3 archive.py install-service
  ```

## 同期・取得範囲・容量の確認

- `status.sync_health` は履歴7経路ごとの最終成功時刻を示します。未確認、または最終成功から10分を超えると遅延です。表示中のHTMLも経過時間を再判定します。ブラウザーでは日時を端末の時間帯で表示します。
- 同期中の約120秒ごとと同期終了時に生成HTMLを更新します。旧分析.xlsxは生成・更新しません。GUI書き出しに失敗した場合は `EXPORT_FAILED` を監査へ残します。
- ジョブの `unavailable` は正常な応答で詳細がnullだったもの、`retry` は通信・応答の異常、`out_of_scope` は指定範囲外、`awaiting_scope` は条件未確認です。`done_final` は保存済みの終了ランキング、`superseded` は他の完全な経路で取得する冗長要求です。
- イベント参加判定は、同じアカウントの試合日時とイベントIDを照合します。保存範囲より前の参加有無は断定しません。オープンの本人詳細とパワー・参加表彰は引き続き保存します。
- `storage_health` が `low`（空き2GiB未満）ならランキングや画像を保留し、最新履歴・試合詳細を優先します。`critical`（512MiB未満）では `STORAGE_CRITICAL` で取得を止めます。ジョブは保持し、容量回復後に再開します。
- `backup` は必要容量を事前検査します。検査済みの一時ファイルだけを保存先に確定し、既存バックアップを上書きしません。途中失敗の不完全なファイルは残しません。
- 強制終了時に残った `running` は、排他ロックを取った次の同期で `interrupted` と記録されます。
