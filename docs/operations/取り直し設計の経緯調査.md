### 重複排除（`Store.record`）が見落としを助けたか

助けた可能性は高い。ただし、「重複排除があるから大丈夫」と明言した原文は G2 の 1 件で、ほかは推論が暗号化または切り詰められていて、考えは確かめられない。根拠は次のとおり。

1. 重複排除の条件に `variables_json` が入っている（store.py:175-176。account、operation、variables_json、body_sha256、http_status、query_id、app_version が全部同じときだけ既存の行を返す）。別名 ID は `vsResultId` が違うので別の応答行になる。応答の本文も、ID の書き方の違い（詳細の `/id`、全プレイヤーの `/…/players/#/id`）で変わる。公開サンプルの ID は `VsHistoryDetail-<ユーザー>:BANKARA:<時刻>_<uuid>` と `VsPlayer-<ユーザー>:BANKARA:<時刻>_<uuid>:<プレイヤー>` の形で、モード名が ID の中に入る（tests/fixtures/public/VsHistoryDetailQuery.json）。つまり「同じ本文は増えない」が当てはまるのは、同じ ID を同じ本文で取り直した場合だけである。
2. テストと設計書は、その場合だけを確かめた。tests/unit/test_fetch_receipts.py:19-33 は、同じ ID・同じ本文の取り直しで responses と bodies が 1 のまま、response_fetches が 2 になることを検査する。設計.md:119 は「同一本文は重複排除し、取得ごとの日時・HTTPヘッダー・runを `response_fetches` に記録する」。別名 ID の対や、同じ試合の documents・jobs の件数を検査するテストは無い（`test_mode_alias_identity` は ID の等価判定だけ）。
3. 「重複しない」は試合の行で満たされた。G1 は L95 の指示を「同じアカウント・操作・引数・本文ハッシュの応答は既存行を返す。試合行は増やさない。」と読んだ（L97）。`matches` は `match_key`（別名を除いた鍵）で一意なので、画面や集計の試合数は重複しない。重複は documents（1 応答ごとに本文の写し）、sightings、asset_refs（1 詳細あたり約 300 行）、response_fetches、jobs の側に出る。
4. 数字は残っていた。documents と matches の件数が、開発ログに 10-01 に 4 回記録されている。「matches 790、documents 1562」（L924、L947、L1129、L1281）。比は 1.98。L1477 は文書 1563。試合 740 件ほどが別名 2 本、コープ約 50 件が 1 本とすると約 1,530 で、記録された 1,562 に近い（私の算術で、推測）。この比を問う記述は、開発ログにも、Codex のアシスタント発言にも見つからない（検索語: 倍、試合あたり、複数の詳細、文書が多い など）。
5. 検査の向きが片方だった。AGENTS.md:9「取得対象の網羅性と保存する全項目の完全性を別々に検査する」、AGENTS.md:27「分割も一切省略禁止」、前田さんの叱責（L1749 ほか）は、いずれも取りこぼしと省略についてだった。多すぎること・同じものを何度も取ることの検査は、規則にも監査にも無い。これが、重複排除が効いている部分だけを見て止まることを許した構造だと考えられる（推測）。

### A14 の「任天堂が取り直しごとに ID の符号化を変える」について

開発ログ L2603 の A14 の測定は「同じ試合の最新2件の詳細の違い（上位40試合）は ID の文字列だけ: /myTeam/players/#/id と /otherTeams/#/players/#/id 各120、/previousHistoryDetail/id 35、/nextHistoryDetail/id 34、/player/id 30、/id 30」で、「任天堂側が取り直しごとに ID の符号化を変えているとみられる」と結んだ。この数字は別名 ID の対で説明がつく。30 の対では、詳細の /id、自分の /player/id、味方 4 人、相手 4 人の ID が全部変わるので、30、30、120、120 になる。取り直しごとに符号化が変わるなら、40 試合のすべてで /id が変わるはずで、30 とは合いにくい。残りの 10 試合は、同じ ID の対で、前後の試合へのリンクだけが変わった（35 と 34 の端数）。これは、今回の Opus が NAS で確かめた結果（同じ ID の差は前後リンク 1 項目、別一覧の ID で取った詳細は ID の書き方も違う）とも合う。元データは私は見ていない。

さらに、アプリ自身が、完全な詳細とは別に、前後リンクだけを取り直す専用クエリ `VsHistoryDetailPagerRefetchQuery` と `CoopHistoryDetailRefetchQuery` を持つ（選択項目は 7 パス: id、__typename、nextHistoryDetail.id、previousHistoryDetail.id。config/query-catalog.snapshot.json）。詳細の中で時間とともに変わりうるのは、アプリの設計の上でも、この前後リンクだけであることを示している（推測）。
