# SQuidLite3 製品形態（設計 0.2・2026-10-05 Opus 5.5）

名称は SQuidLite3（前田さん 2026-10-05）。ドメイン sql3.ink（前田さん取得、Cloudflare Registrar）。

## 前田さんの指示（2026-10-05、要点。全文は開発ログ）

- パソコンに明るくない人でも簡単に扱えるようにする（データを自由自在に利用できるようにする）ことを一番に考える。
- 他のユーザーのデータを前田さんの NAS や Google Drive に載せない（パンクする）。
- 全ユーザーに Google の API 登録のような煩雑な作業をさせない。
- 保存場所はユーザーに用意してもらいつつ、体験はスムーズに。PC 操作が苦手でも、スマホだけでも使えるようにする。
- 計算もユーザー側で動かす。
- UI は NOAHS の方針に従う。

## 判断（0.1 の「Web アプリ（PWA）を自分の機械で配信」を改める）

**ローカルファースト：取得・保存・計算はすべて利用者の端末で行う。**

1. **他の利用者のデータは前田さんの設備に一切置かない。** サーバーは持たない。sql3.ink に置くのは、プログラム本体の配布、案内、プライバシーポリシー・利用規約だけで、記録は置かない。
2. **保存先は利用者が選ぶフォルダ。** クラウドに置きたい人は、OS のクラウド同期フォルダ（Google ドライブ パソコン版、iCloud Drive、OneDrive）を選ぶだけでよい。アプリは普通のフォルダとして書くので、Google の API 登録も鍵も要らない。AI（ChatGPT など）から読みたい人は、そのフォルダを Google ドライブにしておけばよい。
3. **最初の形はデスクトップアプリ（macOS / Windows）。** ダウンロードしてダブルクリックで入り、ターミナルも Python も Node も要らない。中で取得・保存・画面をすべて動かす。初回は対話型の案内（`SQuidLite3_導入案内.md`）を画面で行う。
4. **スマホだけの人向けには、次の段でスマホアプリ（iOS / Android）。** 開いたときに新しい記録を取りに行く（イカリング3には各モードの直近の記録が残っているので、ときどき開けば取りこぼさない）。保存先は iCloud Drive などの OS のフォルダ。デスクトップ版と同じ画面とデータ形式を使う。
5. **前田さんの NAS 運用は、このうち「保存先が NAS、取得を常時動かす」特殊な場合**として残す。NAS から Drive への配信は前田さん個人の設定であり、他の利用者には関係しない。

## ドメイン sql3.ink の使い道

- 公式ページ（何ができるか、ダウンロード、導入の案内）。
- プライバシーポリシーと利用規約。App Store / Google Play の公開や、Google の OAuth アプリの公開に必須で、2026-10-05 に前田さんの Google Drive 認証 ID の公開が止まったのは、まさにこのページが無かったため。
- 更新の配布（アプリが新しい版を確かめる先）。
- 前田さん個人の外出先からの閲覧（例: NAS の画面を Cloudflare Tunnel と本人認証で `my.sql3.ink` などに出す）。

## 技術の方針（Opus 5.5 の判断・2026-10-05。試作で確かめてから確定）

実測: 取得の中核は Python 約5,000行（archive.py、store・collector・planner・classify・rates・records・gui など）と、nxapi を呼ぶ Node の橋渡し約160行。認証を担う nxapi は TypeScript 製で AGPL-3.0（本ツールと同じ）。

1. **第一段（早く届ける）: Electron のデスクトップアプリ。** Electron は Node を内蔵するので nxapi がそのまま動く。Python の取得部は、単体で動く Python（python-build-standalone）を同梱して呼ぶ。利用者は何も入れずにダブルクリックで使える。画面は今の記録閲覧画面を NOAHS の方針で作り直したものを、アプリの窓の中に出す。
2. **第二段（スマホへ）: 取得部を TypeScript に移す。** スマホでは Python も Node の子プロセスも動かせないので、取得の中核を nxapi と同じ TypeScript に書き直し、デスクトップとスマホで共有する。約5,000行で、テスト（公開サンプルと人工データ）をそのまま照合に使える。
3. Tauri 2 は配布物が小さくスマホにも対応するが、Python と Node の両方を外付けで抱える必要があり、第一段の手間が大きい。第二段で TypeScript に移した後なら再検討の余地がある。

## 技術の選び方（次に決める）

デスクトップとスマホを一つのコードで作れる枠組みを選ぶ。候補は Tauri 2 と Electron（＋スマホは別）。取得部は現在 Python と Node（nxapi）で書かれているため、同梱のしやすさ（Node を内蔵する Electron が有利）と、スマホまで同じコードで行けるか（Tauri 2 が有利）を、試作で測って決める。
