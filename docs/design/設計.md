# 設計 0.2

## 目的と完了条件

イカリング3のアカウントから公開される対戦・バイト・各種記録を、ユーザーの指定した取得範囲に従い、取得した応答の項目を落とさず継続して蓄積する。試合情報は自分だけでなく他チーム・他プレイヤー・装備・能力・表彰・追加モード情報を含む。バイト情報は全参加者、各WAVE、支給ブキ、スペシャル、オオモノ、オカシラ、評価・報酬等の返却項目を含む。

「取得済み応答を省略しない」と「取得対象に漏れがない」は別の検査とする。現在のアプリが持つ読み取りクエリを実物から棚卸しし、未対応引数、未取得詳細、未走査ページ、選択されたのに返らなかったフィールド、未取得画像、取得エラーを記録する。認証と実アカウントの照合を終えるまでは全取得完了としない。

サーバー内部に存在していてもアプリへ公開されない情報、取得可能期間から流出した過去記録は、クライアントから存在・完全性を証明できない。全過去試合の復元や任天堂内部DBの全取得を保証する製品ではない。status/auditのall_server_records_verifiedはfalseとし、取得経路の処理完了とは区別する。

## 取得対象を決める仕組み

1. 任天堂のイカリング3のHTMLと同一オリジンのアプリJSを取得する。広告・分析スクリプトは収集しない。
2. Acornで構文木を作り、Relay生成データの純粋なリテラル・配列・オブジェクトだけを読む。ダウンロードしたJSを実行しない。
3. JS内のRequestマーカー数と抽出数を照合する。新しい構文を解釈できず数が合わない場合は失敗し、従来定義で成功したように扱わない。
4. operationKindがqueryのものについて、ルート取得、IDによる関連取得、カーソル・ページ番号の追加取得を構築する。未知の必須変数はunsupportedとして記録する。
5. サーバー状態を変更するMutationは送信しない。分析設定ConfigureAnalyticsQueryと共有用画像生成useShareMyOutfitQueryは保存済みプレイ記録の読み取りではないため、理由を示して除外する。

2026-09-22に取得した現行10.0.0-d15503c4では113操作、query 106、Mutation 7。分析設定・共有画像生成の2経路と、完全詳細クエリの選択項目だけを部分再取得する冗長な1経路を除き、独立した読み取り対象は103経路。数は将来固定しない。configのスナップショットはテスト用で、収集時はライブ定義をDBに保存する。24時間ごと、およびrefresh-catalogで更新する。

対象にはレギュラー、バンカラ、X、フェス、イベント、プライベート、サーモンラン、ビッグラン・バイトチームコンテストの公開記録、ステージ・ブキ・過去シーズン・各種ランキング、ヒーロー、サイドオーダー、カタログ、旅、アルバム、リプレイ情報、マイコーデ等が含まれる。これは取得経路の存在を確認した対象表であり、本人アカウントで全項目の取得成功を確認した表ではない。

## 認証と輸送

nxapi 1.6.1-next.257（上流revision 47c9d35）をnpm標準レジストリから固定導入する。認証、キャッシュ、更新、署名用サービス連携はnxapiの処理を利用する。認証時に利用する外部サービス等はnxapiの動作に従う。アプリ独自のパスワード入力画面は作らない。本人はNintendoのブラウザー画面で認証する。

Nodeブリッジは現行定義のpersisted-query IDで読み取り要求を行う。応答をJSONへ変換してから保存すると数値表現等を失うため、まず本文をバイト列で取得してスプールへfsync・renameし、その後Pythonに通知する。本文は転送圧縮展開後のHTTP entity body。TCP通信・TLS暗号文の保存ではない。認証・Cookieヘッダは保存しない。

401ではnxapiの更新ハンドラを1回呼び再試行する。応答の `x-bullettoken-remaining` が300秒以下、または保存済みbulletの残りが5分以下なら、失敗する前に更新する。429/5xxはRetry-Afterを優先して全体を待機させる。APIレスポンスの一部にエラーがある場合も元本文を保存し、成功とは区別する。秘密を含む可能性のある例外オブジェクトをログへ出さない。

## 認証が切れる条件

再ログインが要るのは、ニンテンドーアカウントのセッショントークンが期限切れか失効したときだけである。2026-09-22にこの端末へ保存したセッショントークンの `iat` と `exp` の差は730日で、残りも約730日だった。トークン本文は記録しない。

それより短い資格情報は、セッショントークンから取り直す。同じ日の実測とnxapiの定数は次のとおり。

- イカリングへ出すbulletトークンは2時間（nxapiの `TOKEN_EXPIRES_IN`）。実測の残りは116分だった。
- Nintendo Switch Onlineの資格情報 `credential.expiresIn` は7200秒。実測の残りは108分だった。
- ニンテンドーアカウントの短いアクセストークン `expires_in` は900秒。実測の残りは3分だった。

これらは各同期の開始時に期限を見て、切れていればセッショントークンで更新する。再起動やスリープではファイルに残ったセッショントークンを使う。電源がオフの間の試合は、その間は取れない。起動後のLaunchAgentが続きを取る。取得窓から出た試合は後から戻らない。

`AUTH_REQUIRED`、`AUTH_EXPIRED`、`SESSION_EXPIRED` は成功にしない。終了コードは1、`runs.status` は `blocked`、`issues` に `AUTH_INCIDENT` を残す。macOSでは通知を出す。同じ失敗の通知は6時間に1回までにする。通信失敗 `NETWORK` は再ログイン扱いしない。`status` の `auth.reauth_required` が真のとき、その区間の戦績は保存できていない。セッション残りが14日未満なら `session_expires_soon` を真にする。

## SQLite構造

- bodies: SHA-256で重複排除した原文バイトと画像バイト。認証情報は含めない。
- responses: 全取得の日時、アカウント、操作、引数、クエリID、アプリ版、HTTP状態、本文参照。変更前の取得結果を保持する。
- manifests: 現行アプリの全操作定義と取得元URL・ハッシュ。
- matches/match_refs/sightings: 対戦・バイトの同定、一覧への登場、詳細未取得の追跡。対戦フィルタ違いのIDは同じ試合キーにまとめる。
- documents: 詳細の改版。canonical detailを更新するのは完全な詳細クエリだけで、pagerや一覧が上書きしない。
- entities/jobs: 型とIDを持つ関連記録、永続取得キュー。1回の実行予算を超えた仕事は残し、次回へ継続する。
- assets/asset_refs: 画像の参照元・保存状態。取得してよいのは https で、ユーザー情報がなく、ポートが空か 443 のものだけである。ホストは nintendo.net、nintendo.com、nintendo.co.jp 自身か、そのサブドメイン。写真アルバムは storage.googleapis.com のバケット ugcstore-toyohr-lp1-persistent だけを許す。ほかのバケットは取得せず、未取得のまま残す。署名の Expires、または X-Goog-Date と X-Goog-Expires が過去の URL は通信せず、未取得のまま残す。
- issues/runs/endpoint_heads/page_fingerprints/control: 実行結果、未対応・欠落・ページング停滞、前回取得との重なり、再試行制御。

all_fieldsはjson_treeによって未知項目を含むJSON木をSQL検索する。null・空配列・空オブジェクトも区別する。SQLiteの数値表現を超える値の正典は原文BLOB/JSONであり、SQL数値変換の結果ではない。表に専用列がなくても原文から失われない。

## 分析の母集団

取得は省略しない。分析するときは次を混ぜない。それぞれ別ビューである。

- ナワバリ `analysis_nawabari`
- オープン `analysis_bankara_open`
- チャレンジ `analysis_bankara_challenge`
- イベマ `analysis_event`
- Xマッチ `analysis_xmatch`
- フェス `analysis_fest`
- プラベは開始時の人数で分ける。4対4、3対3、2対2、1対1、それ以外。2対2はイカップルが行われる枠だが、2対2の試合をすべてイカップルとは記録しない。イカップルにするかは後からのタグである。
- バイト `analysis_salmon_regular`
- ビッグラン `analysis_big_run`
- バイトチームコンテスト `analysis_team_contest`

公開戦で名簿人数が4対4でないものは回線落ちとして、そのジャンルのビューに残す。人数で母集団を分けるのはプラベだけである。フェスのトリカラもフェスに置く。

プラベのエンジョイと対抗戦、オープンの下げラン・練習・エンジョイ・ガチは、APIの区分ではない。`archive.py tag add --match-key ... --tag 対抗戦` で後から付ける。これらの語は候補であり、ほかのタグも付けられる。タグは母集団を動かさない。付いていない試合にタグの行は無い。

正本のほかに、全表・全行・全列・SQLite型・原文バイト・画像・取得状態・監査・スキーマを一切省略しない小分けSQLite群を持つ。モード・モード内ルール別DBは、該当試合の識別子と分類、および全共通データへの参照を持つ入口である。共通データは表ごと・行区間ごとに最大20MiBのSQLite断片へ分け、巨大TEXT/BLOBも型・長さ・SHA-256・順序を保持した値断片へ分ける。各入口のshared_filesに全共通断片の場所・バイト数・SHA-256を保存し、単独の巨大統合DBを依存先にしない。必要な表や値の断片を選んで読み、元の主キー・外部キー・response_id・body_sha256等による関係を保持する。全表の定義、列、インデックス、ビュー、トリガーもmanifestに保存する。直接関係づけられないイベント・機器状態等を捨てたり、試合0件を未参加の証明としない。分類なしはunclassifiedとして全て含める。モード内ルール別は分類済み試合がある全モードと観測された全ルールの直積を作り、0件の組も保存する。統合版・小分けSQLite・全情報xlsxは同じ読み取り静止点と世代を使い、NASとGoogle Driveの全ファイルをバイト数・SHA-256で一致させる。全source対全分割の全値照合、各入口の全参照到達性、世代整合を検証する。件数・値合計の一致だけで完全としない。全検証と遠隔全量読戻しを終えて初めてlatestを更新し、失敗・遅延は直前成功時刻と分ける。収集の書き込みを待たせない独立workerを使い、確定更新を追跡して継続同期する。既存partial世代は保存するが不完全と明示し、完全版として使わせない。旧OMITS付きanalysis_sliceの「原文・画像・取得キューを写さない」設計はユーザー指示に反するため撤回した。

`battles` と `salmon_runs` は所在を辿るビューであり、勝率集計には使わない。区分できない試合は `analysis_hold` に置き、6区分やバイトの通常へ混ぜない。

`archive.py audit` の `event_evidence` は、フェスの個人成績を持つイベント詳細、ビッグランの最高納品数を持つ開催記録、バイトチームコンテストの参加回数欄を、分類済み試合・シフト数とは別に集計する。再取得とページを重複計上しない。フェスはアカウントとイベントID、ビッグランはアカウント・開催期間・ステージIDで区別する。参加回数欄は観測最大値であり、アカウント間の合計でも取得済みシフト数でもない。イベント側に記録があっても、当該試合・シフトの詳細が取得できたことを意味しない。分類済みの該当区分が0件であっても、未参加または過去記録の完全取得とは判定しない。`event_evidence` の出力にはイベントIDやアカウントIDを含めない（`audit` の他項目の公開可否とは別）。

全情報XLSXは `scripts/export_full_xlsx.py` がSQLiteの同一静止点から全表・全行・全列・列定義・スキーマ・外部キー・元rowid・型付き値を出力する。長い原文JSONや画像BLOBも省略せず、セル上限に収まる順序付き断片として全量を保持し、ファイルは20MiB以下へ分ける。INTEGERは10進文字列、REALはfloat.hex、BLOBとXMLで表せないTEXTはbase64で復元可能にする。manifest/indexが全断片と出典静止点の関係を保持し、書出し後に元sourceと全値照合する。差分のXLSXは変更transportを完全に表し、現在の全状態は同じbaselineと順序付き差分chainから復元する。XLSXの編集は正本へ戻らない。旧 `exports/分析.xlsx` と `exports/analysis.xlsx` は情報を省略していたため参照・生成・更新・配信を退役し、既存ファイルは履歴として保全する。旧Macファイル同期はこの2つの正確な相対パスだけを対象外にし、ファイルを削除・移動しない。ほかの拡張子や `exports/` 全体は除外しない。全情報XLSXは専用workerの全値照合・全proof・遠隔全量読戻し後に公開する。旧export-xlsx/published-xlsx CLIはDB/旧表を開かず終了コード4、デスクトップAPIは認証とquery検査後HTTP410を返す。全情報版が検証・公開を終えるまでは画面に準備中と表示し、旧表を代用品として渡さない。

レートの推移は `rate_points` に、応答へ入っているパワー・ポイント・納品数・レートの数値を、名前を閉じた一覧にせず拾う。ルールが違えば系列も分ける。ビッグランとバイトチームコンテストでは納品数を主指標、バイトレートを副指標にする。チョーシはブキ記録の `Weapon.stats.vibes` をそのまま保存する。ブキごとの取得時点系列であり、試合時点への補間や勝敗からの代用はしない。従来の勝敗由来系列は誤りのため派生表から除去し、原文・対戦は保持する。画面は `archive.py gui`。配色は NOAHS の卓上 `#2a0063` と紙 `#fbf5ec` を使い、本文は実測で 4.5 対 1 を超える組だけ、グラフの線は 3 対 1 を超える組だけを置く。

生成HTMLには `assets/fonts/Splatoon2-Unified.otf` をbase64で埋め込み、HTML単体を移動しても同じ書体で表示できるようにする。フォントはNintendoの第三者資産で、AGPLの対象外である。再配布はリポジトリ管理者が取得した許諾に基づく。環境変数 `IKARING_ARCHIVE_FONT` が指定された場合だけ別フォントへ差し替えられる。

グラフは単なる折れ線にしない。縦横の軸、切りのよいY目盛り、水平補助線、最大5箇所の日付目盛り、ゼロ線、面、各点、最終点の強調を持つ。各系列には最新値、直前からの増減、最低、最高、点数を置く。評価ポイントは0〜999を基本目盛りにし、評価レート・獲得ポイント・納品数にこの上限を適用しない。キケン度は原文の比率を保持し、表示時だけ百分率にする。表示値は読みやすい桁へ丸めるが、SQLiteの正本値は変更しない。SVGのtitleとdesc、同じ数値の表、スマートフォン幅の折り返しを保持する。

## 将来の統合GUIとスマートフォンアプリ

現在の `archive.py gui` はレート確認用の生成HTMLであり、全機能GUIではない。将来は、次を同じ利用体験から扱える統合GUIを別工程で作る。

- 収集状態、最終成功時刻、認証事故、未取得ジョブ、取得範囲監査
- ジャンル別の対戦・バイト一覧、詳細、検索、期間・ルール・ブキ等の絞り込み
- プラベとオープンの事後タグ付けとタグ別分析
- レート、勝敗、ルール別成績等の可視化
- xlsx、バックアップ、復元、監査レポート

SQLite正本・収集処理・分類・監査をUIから分離し、デスクトップGUIとスマートフォンアプリが同じアプリケーション層を利用できる構造にする。スマートフォンがPC側の正本へどう接続するかは、認証、暗号化、家庭内ネットワーク限定か外部公開か、同期方式、App Store配布要件を含むため未決定である。安全設計なしにSQLiteやローカルAPIを外部公開しない。

API上の対応は、対戦が vsMode.mode と bankaraMatch.mode、バイトが coop 詳細の rule である。バイト詳細にプライベートバイトを示す欄は現在の取得クエリに無い。rule が REGULAR のバイトへ混ざる可能性がある。実応答で確認するまで、プライベートバイトを分けたと書かない。

## 継続運転と保存先

履歴は毎同期で確認し、完了した関連記録も日次で再取得する。初期値は実行あたり250リクエスト・間隔1.5秒。macOSはLaunchAgentが120秒間隔で起動を試みる。実行中は排他し重複起動しないため、初回の大量取得中は実際の次回開始が120秒より遅くなる。Windows/Linuxは前面watch。停止・スリープ・認証失効中の未保存試合が取得窓から流出する可能性を隠さない。

開発物はリポジトリ、実データは別ディレクトリに置く。既定は~/Documents/イカリング3アーカイブ。SQLiteはWAL・foreign_keys・synchronous=FULL。backupはSQLiteオンラインバックアップで、単純な稼働中DBファイルコピーにしない。バックアップ先の上書きを拒否する。exportは原文バイトと出典manifestを出力する。

## 公開配布と検証境界

GitHubは公開。ZIPから起動できる入口を用意し、Node.js/Pythonが入っていれば依存導入と認証へ進む。認証情報、実戦績、ローカルログ、DBを配布しない。Windows/LinuxのCIはコード経路の検査で、本人認証や外部サービスの可用性を保証しない。

本人認証は完了し、実記録の継続収集を運転している。公開サンプル・人工データ・負例は認証なしで検証する。実アカウントの全経路完了、画面照合、全ページ終端と画像取得の完了は別に監査し、未了のものを完了扱いしない。

## 2026-09-22 継続同期の修正

- 同一本文は重複排除し、取得ごとの日時・HTTPヘッダー・runを `response_fetches` に記録する。再取得ごとにジョブを完了または再試行へ更新する。スプールの同一event_id再生は一度だけ処理し、遅れて届いた古い応答で新しい結果を巻き戻さない。HTTP状態・クエリID・アプリ版が異なる応答は別改版とする。原文書き出しには `fetches.jsonl` を含める。
- 最新履歴7経路を最優先、次に試合詳細、その次にその他記録とする。初回収集が長時間に及ぶ場合も120秒ごとに完了した最新履歴を再確認する。失敗ジョブの再試行時刻・サーバー待機指示は解除しない。
- macOSの既設LaunchAgentはRunAtLoadと120秒間隔を維持する。1回の処理中は書込排他により重複起動を防ぐ。status/audit/verify/sql/backup/export/gui/tag listは、別のSQLite読み取り専用スナップショットを使用し、同期中も利用できる。旧export-xlsxは退役し、CLI入口から拒否する。
- `sync_health` は経路ごとの最終成功時刻を示し、未確認または10分以上古い経路を遅延として表示する。「プロセスがある」ことだけで健全と判定しない。GUIにも確認日時と遅延を表示する。
- 同期中の120秒ごとの更新と同期終了時には、保存済みデータからGUI HTMLだけを自動生成する。GUIは一時ファイルをfsync後に置換し、書き出し失敗時は既存ページを保持する。失敗は `EXPORT_FAILED` として監査する。旧分析.xlsxは自動生成しない。全情報XLSXは収集処理と分離したworkerが同じ静止点から生成し、元sourceとの全値照合・全proof・遠隔全量読戻しが成功した後に公開する。
- 現行の全操作定義には所持ウデマエポイントがない。`earnedUdemaePoint` は保存するが、既定グラフから外す。0からの単純累積を所持ポイントとして表示しない。
- 正式名称は公式日本語辞書、表示順は公式アプリのタブ定義を根拠にする。アカウント・ルール・プライベートマッチの人数区分を跨いで系列を混ぜない。
- 同梱フォントのcmapから得たunicode-rangeを同一SHA-256の場合だけ適用する。「小」「大」「高」「金」等の未収録字は日本語システム書体で補う。「最低」は収録されているが「最高」は全字収録ではない。

## 2026-09-22夜 ランキング範囲と継続運転

オープンとイベントを混同しない。オープンの本人対戦詳細・bankaraPower・参加表彰記録は従来どおり保持する。現行カタログにオープン全体ランキング専用操作は見つかっていない。イベントの期間ランキングは、開催メタデータの日時とイベントIDを同一アカウントのcanonical detailへ照合し、参加を確認できた回のみ取得する。過去の参加記録が取得窓外なら、証拠不在を不参加の確定にしない。メタデータ不足はawaiting_scope、証拠のない回はout_of_scopeとし、証拠追加でpendingへ戻す。既存の原文は範囲変更だけでは削除しない。

Xランキングは終了シーズンのみ。シーズン一覧には本人の値と開催中ランキング先頭が同じ応答に含まれるので、その原文は保持するが開催中ランキングを追加走査しない。4ルール一括ページ番号クエリは組合せが増殖するためsupersededとし、初期詳細＋ルールごとの専用ページングで取得する。終了済みランキングの成功はdone_finalとして日次再取得から外す。現在の103読み取り定義のうち、実際に送信する要求はこの範囲判定を通す。

空き容量2GiB未満は最新履歴・完全試合詳細を優先し、512MiB未満では取得を止める。保留ジョブを削除せず容量回復で再開する。バックアップはpage_count×page_sizeに余裕を加えて事前検査し、完全性検査後にのみ保存先へ確定する。

書き出しは試合ごとの相関SQLを避け、取得した本人詳細を1回ずつ読み、表とグラフを生成する。画像取得にも時間枠を設け、最新履歴の長時間放置を避ける。異常終了runは次の書込み排他取得時にinterruptedへ移す。

NASやクラウドへ大きな保存物を置く場合、稼働中のWALを共有フォルダや同期クライアントへ直接渡さない。確定したDB複製を転送し、サイズ・ハッシュ・SQLite検査後にローカル参照を確定する。稼働DBそのものをNASへ移す場合は、SQLiteを実行する処理も同じNAS上に配置する設計が必要であり、バックアップ転送と区別する。

## NASクライアントと共通読取層

macOSでApplication Supportの `ikaring-archive/client/config/storage-location.json` が存在する場合、通常起動はNASクライアントとして動作する。接続設定が不正でもローカル収集へ戻さない。環境変数 `IKARING_ARCHIVE_DATA_DIR` の明示指定は優先する。クライアントの永続領域には接続設定を置き、要求したHTML/XLSXの表示用コピーは `Library/Caches/ikaring-archive/exports` に置く。Documentsに旧データフォルダを作り直さず、Mac側でDBを作成しない。従来のローカル収集方式は、クライアント設定のない環境で利用できる。

`RecordReader` は統合GUI用の共通読取層であり、既存SQLiteを読み取り専用で開く。一つのcontextの最初の読み取りから終了まで同じスナップショットを用い、例外時も接続を閉じる。別context間の同一スナップショットは保証しない。

一覧の母集合は `matches`。対戦とバイト、詳細未取得、取得不能、未分類の記録を保持する。accountは必須で、kindによる絞り込みと件数制限・offsetを提供する。順序はkindとmatch_keyであり、試合日時順とは扱わない。観測日時first_seen/last_seenを試合日時へ代用しない。未取得のplayed_time、genre、rule等は不明のまま返す。

単件取得は `matches.detail_response_id` が選んだcanonical documentsだけを返す。より新しい部分応答は選ばない。派生JSON文字列と、元のHTTP本文BLOB・出典情報を区別して返し、本文バイトを再直列化しない。一覧ではBLOBを読み込まない。canonical参照先が欠損していれば通常の未取得として隠さずエラーにする。取得状態はavailable、pending、unavailable、unresolvedを区別する。この層の完成だけで統合GUIや取得範囲全体を完成扱いしない。


## デスクトップ記録閲覧の第一段階（実装中）

Mac内の `127.0.0.1` だけで動く読み取り専用画面を追加する。DBの明示指定があればローカルの既存DBを読み、指定がなければ厳密に検証したNASマーカーからSSHで既存CLIを呼ぶ。収集を新たに起動せず、DBをMacへ複製しない。スマートフォン向けの外部接続方式は、この実装では決定しない。

公開する操作は収集状態、アカウント一覧、対戦・バイト一覧、単件詳細の読み取り、および既にあるモード別・ルール別ファイルの固定名での切り替えに限定する。SQLはアカウント列挙用の固定文だけとし、HTTPから任意SQL・DBパス・SSHホスト・コマンドを指定できない。切り替えの値は `unified`、`mode:` に分析セット名、`rule:` に分析セット名とルール名だけである。サーバがその名前を、正本か、正本の隣の `slices/by-mode` と `slices/by-rule` の既知のファイルへ向ける。ファイルが無い名前は開かない。旧分析表の受け渡しは退役し、タグの書き込みは統合版だけである。派生を見ているとき、タグの追加と削除は出さない。記録の読み取りは共通のRecordReaderとrecords CLIを使う。各要求は独立したスナップショットであり、ページをまたぐ同一時点の保証はしない。

起動時に生成した秘密をURLフラグメントで画面へ渡し、画面は読み取った直後にURLから消す。APIはAuthorizationヘッダーで照合し、秘密を永続保存しない。Hostを実際のloopbackアドレスとポートへ固定し、Originがあれば同じoriginだけ許可する。CORSは開放せず、書き込みメソッドは受け付けない。固定したHTML・JS・CSS・同梱フォント以外のファイルを配信しない。CSP、no-store、no-referrerを設定し、HTTPログへ秘密や個人データを書かない。NAS処理には時間と出力サイズの上限を設ける。

画面はアカウントと対戦・バイト種別を選んでページ単位で表示する。詳細未取得・取得不能・未分類を母集合から落とさない。試合日時が不明なら不明と表示し、観測日時で埋めない。未知の値やJSONはテキストとして表示し、HTMLとして実行しない。元応答の保存はbase64をバイトへ戻して行い、数値表記や未知項目をJSONの再直列化で変更しない。切替前の遅延応答を新しい選択へ混ぜない。

この画面から書き込めるのは、プラベとオープンのタグの追加と削除だけである。オープンの候補は下げラン、練習、エンジョイ、ガチ、プラベの候補はエンジョイ、対抗戦、イカップルで、いずれも自由なタグを拒まない。それ以外の試合にはタグ欄を出さない。一覧は、ジャンル、ルール、試合日時、自分のブキ名、タグ、表示項目の文字列で絞れる。一覧と詳細に表示するジャンルは、その分類名である。プラベでは人数区分の名称になる。分類が無い記録は不明と表示する。絞り込みが無いときは詳細未取得と分類なしも残す。期間は詳細の playedTime だけで、観測日時では代用しない。試合日時が無い記録は、期間を指定すると含まれない。ブキは対戦詳細の自分の weapon.name だけを見る。収集状態には、保存試合、詳細が無い試合、詳細待ち、取得不能の詳細、未了のジョブ、監査記録、取得範囲の照合、直近の認証事故、直近の収集エラーを出す。その下に履歴7経路を、最新の履歴、レギュラーマッチ、バンカラマッチ、Xマッチ、イベントマッチ、プライベートマッチ、バイトの順で出す。各行は、確認済みか遅延かと、最終成功時刻か未確認かである。行が無いもの、時刻を読めないもの、サーバが遅延としたもの、表示時点で10分を超えたものは遅延とする。取得中と取得失敗のあいだは、この7行を出さない。表示中は60秒ごとに、同じ取得結果の時刻から描き直す。未了のジョブは pending、retry、awaiting_scope の合計である。取得範囲の照合は all_server_records_verified が真のときだけ照合済みになり、偽のときは未了になる。現在の status はこの値を偽に固定している。件数が整数でないときは未確認と出す。オープンとプラベの人数区分ごとに、試合数、タグなしの試合数、タグごとの試合数を出す。区分をまたいだ合計は出さない。一つの試合に複数のタグがあるときはタグごとに数える。2対2をイカップルにはしない。ルール別の勝敗は、対戦の分析ビューにある試合数、勝ち、負け、引き分け、その他を、区分とルールを分けたまま出す。区分やルールをまたいだ合計は出さない。バイトの納品数は勝敗に入れない。レートは rate_points の系列ごとに、最新、直前からの増減、最低、最高、点数を出す。勝敗から作った系列と、ウデマエポイントの増減は出さない。キケン度は比率のまま保持し、表示のときだけ百分率にする。各系列の数値の下に、軸と目盛りのあるグラフと、同じ数値の表を置く。グラフの目盛りは、別のレート確認画面と同じ規則である。キケン度は、グラフに載せるときも保存値を百分率に変えず、表示の計算だけ百分率にする。1点の系列は線を引かない。旧分析表はこの画面から渡さず、操作を無効にして全情報出力が準備中であることを示す。バックアップ操作は未実装のまま残す。この画面を統合GUIの完成とは扱わない。
